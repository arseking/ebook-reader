# 纸间 TXT 阅读器技术方案

## 1. 目标与范围

将现有网页原型发展为面向个人使用的桌面 TXT 阅读器。首期聚焦本地离线阅读：打开 UTF-8 或常见中文编码的 TXT 文件，查看最近阅读记录，调整字号，并恢复上次阅读位置。书籍内容保留在用户原来的文件中，应用只保存书目和阅读偏好。

首期不做账号、云同步、在线书城、社交功能或 EPUB/PDF 阅读。未来是否扩展格式和同步能力，在首期使用后再决定。

## 2. 技术选型

- **桌面容器：Electron**。现有原型已经使用 HTML、CSS 和 JavaScript，迁移成本低；Electron 也适合使用一套前端代码构建常见桌面平台版本。
- **语言与构建：TypeScript + Vite**。TypeScript 用于约束应用状态和主进程/渲染进程之间的数据接口；Vite 负责开发构建和热更新。
- **界面：沿用现有 HTML/CSS，首期用轻量 TypeScript 组织交互**。当前页面只有书架和阅读器两个主要视图，暂不强制引入 React。等复杂度明显增加、组件和状态管理成为负担时，再引入 React。
- **本地数据：版本化 JSON 文件**。在 Electron 的应用数据目录保存最近阅读条目、阅读进度和界面偏好。数据写入采用临时文件再替换的方式，避免应用异常退出时损坏整个书库。若后续需要大量书籍、搜索或复杂筛选，再迁移到 SQLite。
- **安装包：electron-builder**。用于生成 Windows 安装包；确定 macOS/Linux 发布目标后，再补充相应平台的构建和签名流程。

## 3. 应用结构

应用分为两个进程：

1. **主进程**负责应用窗口、打开文件对话框、读取用户选中的文件，以及访问应用数据目录。
2. **渲染进程**负责书架、阅读排版、字号控制和阅读进度展示。它通过受限的 preload API 请求主进程执行必要的本地操作。

渲染进程不直接访问 Node.js 文件系统 API。界面仅把 TXT 内容当作纯文本显示，避免把文件内容解释成 HTML。应用首期不加载远程页面或远程脚本。

## 4. 核心流程与数据

### 打开和读取

用户通过系统文件对话框选择 TXT 文件。主进程读取文件并将文本交给渲染进程。解码优先尝试 UTF-8；无法按 UTF-8 解码时尝试 GB18030。仍无法可靠解码时，在界面提示用户，而不是静默显示乱码。

首期以常见大小的 TXT 为目标。若后续样本文档显示大文件造成卡顿，再增加分块读取和长文本虚拟化。

### 书目和阅读位置

本地书目记录建议包含：文件路径、显示名称、文件大小、最后修改时间、最近打开时间、阅读进度比例。阅读位置随滚动更新并做短暂防抖后保存；窗口关闭或返回书架时再保存一次。重新打开时若文件已移动或删除，应提示用户重新选择文件。

用户可以调整字号，首期在当前阅读会话应用设置；字号是否跨重启保留，作为界面偏好写入同一本地数据文件。

## 5. 安全和隐私边界

- Electron 窗口启用 `contextIsolation`、`sandbox`，并关闭 `nodeIntegration`。
- preload 只暴露明确的方法，例如选择 TXT、读取已选择文件、载入和保存阅读记录；不向页面暴露通用 IPC 或任意文件读写能力。
- 主进程校验 IPC 调用来源和参数；文件只能由用户通过文件对话框主动选择。
- 不上传书籍正文，不要求登录，不在应用数据中复制原始 TXT 内容。
- 持续跟进 Electron 安全更新，并限制窗口导航和新窗口创建。

## 6. 实施顺序

1. 建立 Electron + TypeScript + Vite 工程骨架，接入现有原型界面。
2. 实现系统文件选择、TXT 解码和阅读视图。
3. 实现本地最近阅读列表、阅读进度恢复和字号偏好。
4. 完成 Windows 打包，检查离线运行、文件丢失提示和常见中文编码显示。
5. 根据实际书籍大小和使用反馈，决定是否需要 SQLite、React、长文本虚拟化或更多格式支持。

## 7. 选择理由与待确认事项

Electron 与当前网页原型和常见前端技能最匹配，便于先交付可用的跨平台桌面版本。主要代价是安装包和运行时占用相对较大。Tauri 可以利用操作系统提供的 WebView 减少随包体积，但需要 Rust 后端，并且各平台 WebView 环境不同；在体积成为实际约束之前，不建议增加这项技术切换成本。

开始工程实现前需要确定首发操作系统，以及是否必须支持 macOS/Linux。除此之外，本文按单用户、本地离线、TXT 优先的范围规划。
